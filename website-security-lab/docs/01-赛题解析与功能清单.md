# 01 · 赛题解析与功能清单

> 赛题：面向网站安全风险评估与敏感信息防泄露的智能巡检智能体（命题企业：杭州安恒信息技术股份有限公司）

---

## 一、命题意图：这道题真正在考什么

命题企业的赛道是**网站安全运营**（安恒的"网站安全监测 / 云监测 / 安全托管运营"产品线）。赛题不是考"会不会用扫描器"，而是考**能不能把一堆开源工具、规则和 LLM 编排成一个持续运营的闭环产品**。三个关键词必须抓牢：

1. **巡检（Inspection）而不是渗透（PenTest）** —— 周期性、覆盖全站、以"发现与跟踪"为目标，不是打点利用。这决定了工具必须默认非破坏性。
2. **智能体（Agent）而不是扫描平台（Scanner）** —— 差异化分数在"任务规划、工具选择与编排、结果关联去重、证据解释、修复建议"上，这五件事恰好是传统扫描器最弱、LLM 最擅长的地方。
3. **闭环（Closed Loop）** —— 发现 → 验证 → 分级 → 告警 → 修复 → 复测 → 报告 → 基线对比。只做"扫出漏洞"的队在功能完整性上最多拿一半分。

赛题里还有一句容易被忽略的前置条件：**"在获得授权的前提下"**。这不是客套话，第 4 项评价指标（安全合规 10%）是硬性门槛，授权边界管理必须做成一个**系统模块**，而不是靠人自觉。

## 二、答题要求逐句拆解

### ① 支持录入授权域名、巡检范围、周期和本单位敏感信息定义

| 子要求 | 系统里必须落地成什么 |
| --- | --- |
| 授权域名 | 授权资产表：域名 / IP 段 / URL 前缀 / 通配子域（`*.example.gov.cn`），含授权编号、有效期、责任人 |
| 巡检范围 | 包含与排除规则（路径黑名单、端口范围、URL 深度、是否跨域跟随跳转） |
| 周期 | 调度表达式（cron / 间隔），含**巡检时间窗**（避开业务高峰）与冻结期 |
| 敏感信息定义 | 四类可配置：**关键词 / 正则（含 PCRE）/ 文件类型 / 样例样本**，支持优先级、白名单、脱敏规则 |

> 关键：**这四项必须是"录入 + 校验 + 生效"的可视化配置**，不是写死在代码里的常量。评委一定会现场新建一个敏感词/规则看是否立即生效。

### ② 自动发现站点页面与资源，按策略调用并编排合规的开源工具，识别常见漏洞、弱配置、恶意外链/挂马、页面篡改及敏感信息暴露

这句话包含 4 个动作、5 类检测目标：

- 动作：**发现 → 采集 → 策略路由 → 工具编排**
- 检测目标：① 常见漏洞 ② 弱配置 ③ 恶意外链/挂马 ④ 页面篡改 ⑤ 敏感信息暴露

注意"**按策略调用**"——隐含要求一个**工具选择策略层**（什么资产特征走什么工具、什么情况降级），这正是"智能体能力 20%"的给分点。

### ③ 对结果去重、验证、分级并给出证据、影响、修复建议，避免破坏性测试

这是全赛题的**质量分水岭**。逐项：

- **去重**：同一漏洞被 3 个工具报 3 次 → 合并为 1 条，保留最可信证据。
- **验证**：区分"疑似/已确认"，对高危结果做**非破坏性二次确证**（例如回显特征比对、安全头缺失复采、文件可访问性校验）。
- **分级**：不能直接用工具自带的 risk 标签，要融合**严重度 + 可达性 + 资产重要性 + 置信度 + 暴露面**。
- **证据**：请求/响应片段、页面截图、diff、命中位置（文件:行）、复现步骤——且**自动脱敏**。
- **影响**：说清"谁能利用、需要什么前置条件、会影响什么业务/数据"。
- **修复建议**：可执行、分角色（开发/运维/安全），含**验证方法**。
- **避免破坏性**：默认安全模式、危险工具禁用、只读优先（详见第 4 节 A6、F6）。

### ④ 支持定时巡检、基线对比、告警、复测和报告导出

五个功能缺一不可，且要形成状态机：

```
定时触发 → 巡检 → 基线对比（新增/变化/消失） → 分级告警
        → 修复 → 复测（按同一检测项重放） → 标记已闭环/仍复现 → 报告归档
```

### ⑤ 提交系统架构、工具清单、演示环境、源代码/部署说明及测试报告

属于**文档类得分项**，必须在交付物里显式存在（本仓库的 `docs/` 就是为这五项准备的）。

### ⑥ 智能体可在恒脑安全智能体平台中运行

意味着架构上要把"智能体大脑"与"工具执行体"解耦：大脑负责规划/推理/解释，执行体以**可注册的工具（MCP / HTTP / CLI 包装）**形式接入平台，避免强绑定自研 Web 界面。

## 三、评分指标 → 功能映射

| 指标 | 权重 | 评委实际看什么 | 对应模块 |
| --- | --- | --- | --- |
| 功能完整性 | 25% | 资产发现是否覆盖子域/JS/接口；周期任务是否真跑；敏感信息是否可自定义；告警与报告是否闭环 | 板块 2、6、7 |
| 检测效果 | 30% | 统一测试集上的**召回率 / 准确率 / 误报率** | 板块 4 检测引擎 + 板块 3 去重验证 |
| 智能体能力 | 20% | 规划是否合理、工具选择是否有依据、去重关联、证据与修复建议质量 | 板块 3 智能体核心 |
| 安全合规 | 10% | 授权边界、限速、最小权限、日志审计、非破坏 | 板块 1 + 板块 8 |
| 工程化与创新 | 15% | 一键部署、稳定性、插件化扩展、可视化、创新点 | 板块 8 |

> 战术提示：**30% 的检测效果是唯一"可以靠工程手段刷分"的指标**。做法是"多工具交叉 + 严格去重 + 保守置信度 + 高危必验证"。宁可少报不可误报——企业对误报的容忍度远低于个人赛。

## 五、演示与验收要点（评委视角）

建议按这个顺序演示，正好对上 5 个评分项：

1. **录入**（功能完整性）：新建一个授权域名 + 一条自定义敏感信息正则 + 5 分钟周期任务。
2. **发现**（功能完整性）：展示子域/页面/资源清单，展示 JS 里挖出来的接口。
3. **检测**（检测效果）：三类各命中 1 条真实结果，并**当场展示去重前后数量对比**（最能体现效果与智能体能力）。
4. **解释**（智能体能力）：打开一条高危，展示工具选择理由 + 证据 + 影响 + 修复建议。
5. **合规**（安全合规）：展示 scope 拦截日志——故意输入范围外域名，看系统拒绝执行。
6. **闭环**（功能完整性）：改一处页面 → 再跑一次 → 展示基线对比"新增变更" + 告警 + 复测状态 + 导出报告。

## 六、常见失分陷阱

| 陷阱 | 后果 |
| --- | --- |
| 把工具输出直接当结果 | 误报爆炸，检测效果 30% 直接崩 |
| 只做单次扫描、无调度无基线 | 功能完整性丢分，"巡检"变"扫描" |
| 敏感信息写死在代码里 | 自定义能力不达标 |
| 无授权校验，任意域名可扫 | 安全合规 10% 归零，且有法律风险 |
| 报告只有列表没有证据与整改建议 | 智能体能力项得分低 |
| 高并发无限制、跑激进 POC | 被判破坏性测试，合规项扣分甚至取消资格 |
| 只能用自研界面，无法接入恒脑平台 | 答题要求 ⑥ 不满足 |

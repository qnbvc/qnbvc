# 08 · 已落地架构（As-Built）

> 这是**平台上真实跑起来的**框架，不是设计稿。与 `docs/02`（设计版）的差别在于：这里每个节点都注明了实现方式、真实产出与当前状态。

---

## 一、一句话定位

在恒脑安全智能体平台上，用 **9 个节点**串起一条可运行闭环：

**授权配置 → 合规校验 → 页面发现 → 三类检测 → 去重验证分级 → 证据与建议 → 报告与告警 → 人工复核 → 归档**

全部检测能力由**代码节点**实现（可联网、可跑正则、可调模型），平台负责编排、人机交互与输出。

## 三、数据流

```
① 开始
   │ ctx
   ▼
② 交互_授权与规则 ── 6 个问答参数 ──┐
   │                                │
   ▼                                │
③ 代码_合规闸门 ◄───────────────────┘
   │ result_key = {scope_snapshot, sensitive_rules, valid, errors, …}
   ├──────────────► ④ 代码_资产与页面发现
   │                  │ result_key = {pages[含 content_hash], assets, stats, blocked}
   │                  ▼
   └──────────────► ⑤ 代码_三类检测 ◄── (pages + rules)
                      │ result_key = {findings, stats, skipped}
                      ▼
                    ⑥ 代码_去重验证分级
                      │ result_key = {findings[去重+置信度+等级], stats}
                      ├──► ⑦ 模型_解释与建议（当前空转）
                      ▼
                    ⑧ 代码_报告生成与告警 ◄── ④ 的 discover_payload
                      │ result_key = {summary, report{markdown,html}, alert, debug}
                      ▼
                    ⑨ 交互_复核与复测
                      │ review_action / review_note
                      ▼
                    ⑩ 结束 ──► 对外输出 6 项参数
```

**真实变量名**（节点间引用时用这些）：

| 变量 | 产出节点 | 消费节点 |
| --- | --- | --- |
| `gate_payload` | ③ | ④、⑤ |
| `pages_payload` | ④ | ⑤、⑧ |
| `rules_payload` | ③ | ⑤ |
| `findings_payload` | ⑤ | ⑥ |
| `explain_payload` | ⑦（可选） | ⑧ |
| `discover_payload` | ④ | ⑧ |

> ⚠️ 平台"引用"上游参数时会包一层 `{"result_key": <值>}`，所以**每个代码节点内部都有 `_unwrap()` 剥壳**——这是本项目的关键工程经验。

## 四、三个横切机制

### 1. 合规闸门（贯穿三层，请求前短路）

| 层 | 位置 | 拦什么 |
| --- | --- | --- |
| 配置层 | ③ 合规闸门 | 裸通配、非法域名/CIDR、坏正则、白名单冲突、超范围数值 → 直接 `valid=0` |
| 执行层 | ④ 内建 `Scope` | 非授权主机、命中排除路径/规则、重定向落点出范围 → **不发请求**，记入 `blocked` |
| 档位层 | ⑤ `_scan_exposure` | 只对 `active_assets` 显式授权的资产做 T1 探测，其余记 `skipped` |

**可演示证据**：把首页加入排除路径 → 日志显示"**请求 0 次 / 拦截 1 次**"，证明请求在出站前就被短路。

### 2. 解释生成的三级降级

```
⑦ 模型节点产出 → ⑧ 自调 HengNao-v4 → 内置修复模板
```

任一环节不可用时自动降级，**保证报告的影响与建议永不缺失**。`debug` 字段会记录实际走了哪一级。

### 3. 去重与验证（决定报告可信度）

- **聚合键**：`类型 + 规则 + 位置`，跨页面合并为一条并列出 `affected_urls`（例：24 条弱配置 → 6 条）
- **非破坏性确证**：只读复采原页面，命中仍在 → `confirmed`；已消失 → `needs_review` 并降置信度
- **分级公式**：`风险分 = 严重度 × 可达性 × 资产重要性 × 置信度` → 映射 P0~P3
- **报告可量化**：明确写出"原始命中 N → 去重后 M（压缩 X%）"

## 六、已实现 vs 待补

### 已实现

- 授权录入与范围校验（含排除规则、host:port、CIDR）
- 页面发现（同站 BFS、链接/资源提取、内容哈希、HTTPS→HTTP 回退并记为风险信号）
- 四类确定性检测（敏感信息 / 弱配置 / 挂马特征 / 暴露面）
- 去重聚合 + 非破坏性确证 + 风险分级
- 模型生成影响与整改建议（分角色 + 验证方法）
- Markdown + HTML 双格式报告
- 分级告警（P0/P1 触发）与人机复核

### 待补（按优先级）

| 事项 | 依赖 | 预估 |
| --- | --- | --- |
| **第二轮：基线对比 + 篡改检测** | 基线持久化（知识库写入 或 入参回传） | 半天 |
| **定时巡检** | 平台的触发器/定时任务入口 | 待确认 |
| 告警通道实发 | 填 Webhook 地址（webhook.site / 企业微信机器人） | 5 分钟 |
| 报告在对话内展示 / 文件导出 | 变量引用路径（`$.result_key`）打通 | 1 小时 |
| 时间窗强制校验 | 代码补 ~10 行 | 20 分钟 |
| ⑦ 模型节点修复或移除 | 变量作用域路径 | 10 分钟 |
| 提交物：工具清单 / 部署说明 / 测试报告 | 本仓库 `docs/` 已有素材 | 1 天 |

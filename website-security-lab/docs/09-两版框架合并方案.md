# 09 · 两版框架合并方案

> 输入：`智能体解读报告.md`（ID 2108504161902698498，6 节点）与 `网站安全智能巡检官-智能体总结.md`（ID 2109296360672239618，10 节点）
> 目标：**只保留两版中有用的节点，明确每个节点的变量，得出一个可落地的合并框架。**

---

## 一、两版对比：各有什么、各缺什么

| 维度 | v1（2108…，6 节点） | 巡检官（2109…，10 节点） | 合并取舍 |
| --- | --- | --- | --- |
| **工具编排** | ⭐ 自规划节点挂 **14 个 MCP + 5 个 Skill**（Nuclei/Nmap/SQLmap/TLS/子域…），真正"调用开源工具" | ❌ 全靠自写 Python，**没有调任何外部工具** | **必须保留 v1 的这条**——赛题要求②明确写"编排开源安全工具" |
| **授权确认** | ⭐ 交互节点有 `auth_confirmed` **单选**（✅已获授权 / ❌暂无 / 🔍仅了解） | ❌ 没有显式的授权确认动作 | **吸收**——合规刚需，也是答辩最容易被问的点 |
| **默认值预设** | ⭐ 开始节点预设 11 个业务变量（敏感词/文件类型/正则/QPS/UA/工具白名单/告警通道…） | ❌ 全靠每次手填 | **吸收**——"本单位敏感信息定义"就该是预设 + 本次覆盖 |
| **敏感定义合并** | ⭐ 三级合并：本次问答 > 开始节点默认 > 样例提炼 > 内置默认 | ❌ 只有本次录入 | **吸收**——降级设计，很专业 |
| **检测项** | ⭐ 多出：Cookie 属性、CORS `*`+credentials、目录列表、**simhash 汉明距离判篡改** | 四类规则（敏感/弱配置/挂马/暴露面），但**只看内容哈希** | **合并**——v1 的判定更细 |
| **结果处理** | 代码内自行去重排序 | ⭐ **跨页面聚合 + 非破坏性复采确证 + 风险分公式** | **保留巡检官的**——比 v1 的"去重排序"强一档 |
| **AI 解释** | ❌ 无 | ⭐ 模型生成影响/建议，且**三级降级**（模型节点→自调→模板） | **保留巡检官的** |
| **报告与告警** | ❌ 结束节点**未配置** | ⭐ Markdown+HTML 双报告 + 分级告警 + 可读文本输出 | **保留巡检官的** |
| **响应通道** | ⭐ 交互收集 `alert_channel` | ❌ 告警通道写死在代码里 | **吸收** |
| **运行状态** | ⚠️ 自规划节点**运行失败** | ✅ **全部节点运行成功** | 以巡检官为主线骨架 |

**一句话结论**：以**巡检官为主线骨架**（它跑通了），把 v1 的**授权确认、默认值预设、敏感定义三级合并、检测增强、MCP 工具编排**补进去。

## 二、合并原则（三条）

1. **主线用跑通的**——巡检官的 10 节点链路是已验证资产，不推翻，只做加法。
2. **补上战略缺口**——"编排开源安全工具"是赛题硬要求，v1 的 MCP 分支必须并进来（并行分支，不阻塞主线）。
3. **口径统一**——两版最大的坑是 v1 的**工具白名单前后不一致**（开始节点写 httpx/katana，自规划提示词却禁用它们）。合并后**以 MCP 实际可用的工具为准，全流程只维护一份清单**。

## 三、合并后的框架（11 个节点 + 1 个并行分支）

```
① 开始节点（输入 + 业务默认变量）
      │ input / trigger_type / target / request_id + 11 个默认值
      ▼
② 交互·授权与规则（12 问：授权确认 + 巡检参数 + 敏感定义 + 告警通道 + 任务模式）
      │ auth_confirmed / auth_targets / scan_exclude / schedule_cron / sensitive_* /
      │ alert_channel / task_mode
      ▼
③ 代码·策略校验与上下文构建          ← v1 的 0QR7cO 精华 + 巡检官的合规闸门
      │ scope_snapshot / sensitive_rules / task_id / audit_log
      │
      ├──────────────────────────────┬──────────────────────────────┐
      ▼                              ▼                              │
④ 代码·资产与页面发现            ⑤b 自规划·工具编排（MCP）           │
   pages[] / assets / baseline      tool_findings[] / tool_audit[]   │
      │                              │                              │
      ▼                              │                              │
⑤ 代码·被动检测                     │                              │
   raw_findings[]                   │                              │
      └──────────────┬───────────────┘                              │
                     ▼                                              │
            ⑥ 代码·归一化去重分级 ◄─────────────────────────────────┘
               findings[] / changes{}
                     ▼
            ⑦ 模型·解释与建议（可选，⑧ 有三级降级兜底）
                     ▼
            ⑧ 代码·报告生成与告警
               final_report / alert_receipt
                     ▼
            ⑨ 交互·复核与复测
               review_action / review_note
                     ▼
            ⑩ 结束节点（输出 5 项）
```

**关键结构**：④⑤（被动链路，已跑通）与 ⑤b（主动工具链路，需调通）**并行**，在 ⑥ 汇合去重。**⑤b 挂了不影响主线**——这正是 v1 用"失败后继续"的思路，我们把它做成**分支隔离**，比"失败后继续"更干净。

## 四、逐节点：职责 + 变量

### ① 开始节点

| 输入参数 | 类型 | 说明 |
| --- | --- | --- |
| `input` | String | 用户指令（必填） |
| `trigger_type` | String | manual / schedule / api |
| `target` | String | 指定目标，留空则全量 |
| `request_id` | String | 幂等键 |

**业务默认变量**（本单位预设，本次问答可覆盖）：

| 变量 | 默认值示例 |
| --- | --- |
| `sensitive_keywords` | `身份证,手机号,银行卡,内部系统,数据库连接,账号密码` |
| `sensitive_filetypes` | `.env,.sql,.bak,.zip,.log,.git` |
| `sensitive_regex` | `1[3-9]\d{9}` / `\d{17}[\dXx]` |
| `rate_limit_qps` | `5` |
| `max_concurrency` | `3` |
| `request_timeout` | `30` |
| `user_agent` | `SiteSecurityInspector/1.0 (+authorized-scan)` |
| `tool_whitelist` | **以 MCP 实际可用清单为准**（见 ⑤b） |
| `blocked_methods` | `POST,PUT,DELETE,PATCH,爆破,提权,上传` |
| `alert_channel` | `webhook:https://…`（留空=不推送） |
| `run_status` | `running` |

> ⚠️ v1 的 `baseline_dir=/data/baseline` 在平台上没有意义（节点间无共享磁盘），**改为由 ⑩ 输出 `baseline` 参数回传，或存入平台知识库**。

### ② 交互·授权与规则（12 问）

| # | 问题名 | 类型 | 来源 |
| --- | --- | --- | --- |
| 1 | `auth_confirmed` | **单选** | ⭐ v1：「✅已获书面授权 / ❌暂无授权 / 🔍仅了解功能」 |
| 2 | `auth_targets` | 填空 | 巡检官 |
| 3 | `scan_exclude` | 填空 | 巡检官 |
| 4 | `schedule_cron` | 填空 | ⭐ v1（留空=仅手动） |
| 5 | `sensitive_keywords` | 填空 | 巡检官（留空则用 ① 的默认值） |
| 6 | `sensitive_regex` | 填空 | 巡检官（**多条用分号分隔**） |
| 7 | `sensitive_filetypes` | **多选** | ⭐ v1：`.env / .sql / .bak / .zip / .log / .git / .xlsx / 其他` |
| 8 | `sensitive_samples` | 填空 | 巡检官（**不用单文件类型**——它会卡住流程） |
| 9 | `alert_channel` | 填空 | ⭐ v1 |
| 10 | `task_mode` | **单选** | ⭐ v1：`full / retest / baseline` |
| 11 | `scan_scope` | 填空 | 巡检官（留空= `/`） |
| 12 | `review_needed` | 单选 | 巡检官：是否需要人工复核（是/否） |

**输出**：以上 12 个参数 + `_error_code` / `_error_message`。

> **第 1 问是关键**：`auth_confirmed ≠ ✅已获授权` 时，③ 直接返回 `AUTH_DENIED`，不进入巡检。

### ③ 代码·策略校验与上下文构建

| 输入变量 | 来源 |
| --- | --- |
| ② 的全部 12 个问答 | ② 交互节点 |
| ① 的 11 个默认变量 | ① 开始节点 |

| 输出变量 | 说明 |
| --- | --- |
| `scope_snapshot` | 授权边界唯一依据（域名/排除路径/时间窗/档位/QPS/预算） |
| `sensitive_rules` | 合并后的敏感规则集（三级合并结果） |
| `task_id` / `run_id` | 本轮唯一标识 |
| `audit_log` | 放行 / 拦截审计 |
| `status` / `error_code` | `OK` / `AUTH_DENIED` / `OUT_OF_SCOPE` / `INVALID_INPUT` |

**合并要点**：
- 吸收 v1 的**授权闸门**（`auth_confirmed` 校验）+ **参数夹逼**（QPS 1–20、超时 3–120）
- 吸收 v1 的**敏感定义三级合并**：本次问答 > ① 默认值 > 样例提炼 > 内置默认
- **砍掉** v1 脚本里硬编码的 `AUTHORIZED_WHITELIST=["example.com"]` —— 授权范围只能来自 ② 的录入

### ④ 代码·资产与页面发现

| 输入变量 | 来源 |
| --- | --- |
| `gate_payload` | ③ result_key |
| `baseline_payload` | 上一轮的 `baseline`（可选，**必须显式接线**） |

| 输出变量 | 说明 |
| --- | --- |
| `pages[]` | `url / status / depth / content_hash / simhash / title / headers / text` |
| `assets[]` | 主机 + 页面数 + 状态码 |
| `blocked[]` / `errors[]` | 合规拦截与失败记录 |

**合并要点**：给每页**同时算 `content_hash` 和 `simhash`**（v1 的 simhash 抗噪，巡检官只有 hash）。

### ⑤ 代码·被动检测（四类规则）

| 输入变量 | 来源 |
| --- | --- |
| `pages_payload` | ④ result_key |
| `rules_payload` | ③ result_key（取 `sensitive_rules`） |

| 输出变量 | 说明 |
| --- | --- |
| `raw_findings[]` | 未去重的原始命中（每条含 `type / rule_id / severity / evidence / verify_hint`） |
| `skipped[]` | 未覆盖维度（如"无基线，跳过篡改比对"） |

**合并要点**：在现有四类（敏感信息 / 弱配置 / 挂马特征 / 暴露面）基础上，**补 v1 的三项**：
- Cookie 属性缺失（`HttpOnly` / `Secure` / `SameSite`）
- CORS `Access-Control-Allow-Origin: *` 且带 credentials
- 目录列表（`Index of /` 特征）

### ⑤b 自规划·工具编排（并行分支，MCP）

| 输入变量 | 来源 |
| --- | --- |
| `scope_snapshot` | ③（授权边界，提示词里必须重申） |
| `pages_payload` | ④（已发现的目标清单） |
| `tool_whitelist` / `blocked_methods` | ① 默认变量 |

| 输出变量 | 说明 |
| --- | --- |
| `tool_findings[]` | 工具产出的原始结果（Nuclei 模板命中、TLS 配置、子域、端口等） |
| `tool_audit[]` | 调了哪些工具、参数、耗时、成败 |
| `uncovered[]` | 失败或跳过的工具（如实登记"未覆盖范围"） |

**合并要点**：
- **工具清单以实际可用的 MCP 为准**（v1 的 14 个 MCP 里有 Nuclei/Nmap/SQLmap/TLS/子域发现，够用了），**删掉** ① 里那份自相矛盾的白名单
- 提示词保留 v1 的硬约束（只读、限速、只用白名单内工具、失败重试 1 次后记入 `uncovered`）
- **`SQLmap` 默认禁用**（属于主动注入，赛题要求"避免破坏性测试"）
- 该分支**失败不阻塞主线**（异常策略：失败后继续）

**合并要点**：保留巡检官的**跨页面聚合 + 非破坏性复采确证 + 风险分公式**；把 v1 的 **simhash 汉明距离 > 6 判篡改** 并进来作为 `tamper` 类判定。

### ⑦ 模型·解释与建议（可选）

**合并要点**：保留三级降级（⑦ → 自调模型 → 内置模板）；告警通道改为读 `alert_channel`。

## 五、全局变量清单（按用途分三类）

### A. 业务默认值（① 开始节点声明，本次问答可覆盖）

```
sensitive_keywords / sensitive_filetypes / sensitive_regex
rate_limit_qps / max_concurrency / request_timeout / user_agent
tool_whitelist / blocked_methods / alert_channel
```

### B. 业务状态（流程写入，下游读取）

```
# 标识与模式
run_id / task_id / task_mode / trigger_type / request_id
# 授权与规则
auth_config / scope_snapshot / sensitive_rules
# 发现与检测
assets / pages / raw_findings / tool_findings / uncovered
# 结果
findings / changes / final_report / baseline
# 运行控制
audit_log / request_count / run_status
```

### C. 用户输入（`kv_user`）

```
input / trigger_type / target / request_id
```

**平台变量作用域的坑（务必记住）**：

1. 节点间**引用上游 `result_key`** 时，平台会包一层 `{"result_key": <值>}` → 代码节点里必须用 `_unwrap()` 剥壳；
2. **回答内容/提示词里能引用的只有工作流变量**（① 里声明的那些），不是任意节点输出 —— 所以要在回答里展示 `final_report`，必须先在 ① 里声明同名变量；
3. 代码节点想输出工作流变量，`return` 里要**带同名顶层键**（`{"result_key": …, "final_report": …}`），不能只输出 `result_key`。

## 六、砍掉了什么（及理由）

| 砍掉 | 来自 | 理由 |
| --- | --- | --- |
| `AUTHORIZED_WHITELIST` 硬编码域名 | v1 | 授权范围必须来自人工录入，不能写死在代码里 |
| `baseline_dir=/data/baseline` | v1 | 平台上无共享磁盘，基线改为参数回传或知识库 |
| 开始节点的 `tool_whitelist` 旧清单 | v1 | 与自规划提示词自相矛盾，统一以 MCP 实际清单为准 |
| `sensitive_samples` 的**单文件类型** | 巡检官 | 单文件类型**会卡住流程**（无跳过入口），改为填空 |
| 自规划节点作为**串行必经环节** | v1 | 它运行失败了；改为**并行分支**，失败不阻塞主线 |
| SQLmap 主动注入 | v1 的 MCP 清单 | 属破坏性测试，与赛题要求③冲突，默认禁用 |

## 七、落地顺序（建议）

| 阶段 | 动作 | 产出 |
| --- | --- | --- |
| **第 1 步**（今天） | 合并 ①②③：加授权确认、默认值变量、12 问；③ 补三级合并与参数夹逼 | 配置层就位 |
| **第 2 步** | 统一 `tool_whitelist` 口径；合并检测增强（Cookie/CORS/目录列表/simhash） | 检测能力增强 |
| **第 3 步** | 单独调通 **⑤b 自规划 + MCP**（先只挂 2 个工具：Nuclei + TLS 检测） | 打通"真工具编排" |
| **第 4 步** | ⑥ 接线 `tool_findings`；⑩ 显式输出 5 项；基线用 `baseline` 参数回传做第二轮 | 闭环 + 复测 |
| **第 5 步** | 跑四个测试用例（正向 / 合规拦截 / 自定义规则 / 非法配置），记录测试报告 | 提交材料 |

**风险提示**：第 3 步是**最大的不确定项**（v1 已经失败过一次）。建议**先只挂 1 个 MCP 工具跑通一条最小链路**，再逐个加，不要一次把 14 个都挂上。

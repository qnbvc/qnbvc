# ⑤b 工具线接线与排障

## 一、结论先行

自规划（Agent 类）节点在本平台**没有单节点调试**，这是平台限制，绕不过去。
但 ⑤b 不需要单测，因为它被设计成"挂掉也不影响主线"：

1. 异常配置 = 失败后继续 + 自定义返回 `{"result_key": "[]"}`；
2. ⑥ 对它的入参做容错解析，解析不出来就当"没有补充结果"；
3. 它自己的输出会完整出现在运行日志里，跑一次全流程就能看到。

所以正确姿势是：**把 ⑤b 串进主线跑全流程，然后看日志**，而不是想办法单测它。

## 二、接线

```
④ 资产发现 ──▶ ⑤ 三类检测 ──▶ ⑤b 自规划·工具编排 ──▶ ⑥ 去重验证分级 ──▶ ⑦ ──▶ ⑧ 报告告警
```

要点：

- ⑤ 到 ⑥ 之间**只保留 ⑤b 这一跳**，不要同时留 ⑤→⑥ 直达边；
- 5b 的出边只能有一条出向 ⑥；
- 所有出边的"是否并发执行"全部关闭，否则边条件会被忽略。

## 三、输入参数绑定表（错一个就静默取空值）

| 节点 | 参数名 | 引用来源 | 必填 |
| --- | --- | --- | --- |
| ⑥ | `findings_payload` | **⑤ 三类检测** | 是（主线） |
| ⑥ | `tool_findings_payload` | ⑤b 自规划·工具编排 | 否 |
| ⑧ | `findings_payload` | ⑥ 去重验证分级 | 是 |
| ⑧ | `discover_payload` | ④ 资产与页面发现 | 是 |
| ⑧ | `explain_payload` | ⑦ 风险解释 | 是 |
| ⑧ | `alert_channel` | ② 交互节点收集的变量 | 否 |

最容易踩的坑：**插入 ⑤b 之后，⑥ 的 `findings_payload` 被顺手改成了 ⑤b**。
这时 ⑥ 拿到的是工具线输出而不是 ⑤ 的检测结果，报告就会变成 0 条风险。

## 四、排障三看法

跑完一轮，按顺序看运行日志里这四个节点的运行结果：

1. **④**：`stats.pages` 是否 ≥ 1 —— 报告的"覆盖 N 个页面"就来自这里；
2. **⑤**：`stats.findings` 有几条 —— 测 `fangxiangji.gymjilv.cn` 应该是 5~7 条；
3. **⑤b**：输出是 JSON 数组、中文段落、还是 `[]`；
4. **⑥**：日志里新增的两行诊断，直接告诉你哪条线是空的：

```
[去重验证分级][诊断] findings_payload（应为 ⑤ 三类检测）：字符数=0 / 空值（上游未产出 / 引用绑错节点）
[去重验证分级][诊断] tool_findings_payload（应为 ⑤b 工具线，可空）：字符数=2 / JSON 数组，元素 0 个
[去重验证分级] 原始命中 5 → 去重后 5（压缩 0%）/ 确证 5 / 待复核 0 / P1 2、P2 2、P3 1
```

判定规则：

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| ⑤ 有 5~7 条，⑥ 诊断里 `findings_payload` 是空值 | ⑥ 的引用被绑到 ⑤b 了 | 把 `findings_payload` 改回引用 ⑤ |
| ⑤ 本身就是 0 条 / 报错 | 问题在 ⑤（抓取失败、域名不在授权范围） | 看 ⑤ 的 errors 与 ③ 的授权快照，和 ⑤b 无关 |
| ⑤b 输出是中文段落 | 提示词没约束住输出格式 | ⑥ 会忽略它，主线仍正常；要合并结果需让 ⑤b 只输出 JSON 数组 |
| ⑤b 输出 `[]` | 工具没发现新问题（TLS 正常时就是 `[]`） | 正常现象，不是故障 |

## 五、探针节点：平台没有单测时的通用手段

`framework/platform/probe_code_node.py` 是一个纯文本回显节点，可以插在任意位置：

1. 给它加输入参数 `probe`，引用要观察的节点输出（还能加 `probe2`、`probe3`）；
2. 上游连到探针，探针连回原来的下游；
3. 跑一次，看探针的运行结果：字符数、类型、顶层键、开头 200 字；
4. 排完障把探针从画布摘掉（它不改变任何数据，也不发请求）。

它要回答的问题只有一个：**这个节点的输出，到底是不是下游期望的形状**。

## 六、⑦ 模型节点卡在"运行中"

现象：⑥ 显示运行成功，⑦ 一直转圈，流程停在这一步不动。

根因：⑦ 拿到的输入是空的或不是 JSON，而它的提示词要求"必须输出 JSON 数组、覆盖每一条风险"。
轻量模型在空输入 + 强约束下会空转，节点就一直不返回。这不是 ⑦ 的 bug，是输入为空触发的。

而输入为空的源头，往往是 ⑥ 的主线断了：

- ⑤ 三类检测没有入边/出边，根本没执行；
- ⑥ 的 `findings_payload` 引用的不是 ⑤，或引用已失效；
- ⑥ 此时会"优雅失败"——运行状态是成功，但 findings 是空数组。

处理顺序：

1. 修连线：`④ → ⑤ → ⑤b → ⑥`，⑤b 夹在 ⑤ 和 ⑥ 中间，不要出现 `④ → ⑤b` 这种旁路；
2. 看 ⑥ 的诊断日志：`findings_payload` 字符数必须大于 0，`原始命中` 必须非 0；
3. 给 ⑦ 配异常处理：失败后继续 + 自定义返回 `{"result_key": "[]"}`。⑧ 本身有三级降级（上游 ⑦ → 自调模型 → 内置模板），所以 ⑦ 卡住不该拖死整条线；
4. 若 ⑦ 反复卡住，先检查提示词里有没有"不要/禁止/必须严格"这类否定式强约束——历史上有一次卡死就是它引起的，删掉即恢复。

## 七、工具线结论怎么定性（直接关系误报率）

⑤b + MCP 给出的结论，默认**不算已确证**：

- 有 `verify_hint` 的（例如"敏感文件可匿名访问"），⑥ 会复采一次，命中才算 confirmed；
- 没有 `verify_hint` 的（例如 sslscan 判断的"证书链验证失败"），⑥ 只标 `unverified`，
  置信度不抬高，证据里追加一句"工具线结论，未做独立复采确证，建议用同一工具复测后再定性"。

报告里每条风险都会标注 `检测来源：被动检测线（⑤）` 或 `工具线（⑤b + MCP）| 工具名`，
运行数据里还有一行来源构成，方便评委看到"两条线各自贡献了什么"。

典型例子：`SSL_TLS.SELF_SIGNED / 证书链验证失败` 是工具线结论。如果浏览器访问该站点证书正常、
只有 sslscan 报 `unable to get local issuer certificate`，多半是扫描器本地 CA 库不全造成的误报，
应把这条降级或转人工复核。人工确认方式：浏览器点开地址栏锁头看证书链，或
`openssl s_client -connect 域名:443 -servername 域名 -showcerts`，看返回的是不是完整的叶子+中间证书。

## 八、报告里出现了"不存在的域名"

现象：某条风险的"位置"写成 `https://fangxiangji.bymjilv.cn/`，实测域名是 `fangxiangji.gymjilv.cn`
（g 变 b）。这不是检测错误，是模型在写文本时把域名抄错了一个字母——报告里一旦出现不存在的资产，
整条证据链就不可信，也直接影响"证据可解释、可追溯"的评分。

规则：**位置、规则、证据、风险分这些字段只能来自 ⑥ 的结构化输出，模型只写"影响"和"修复建议"。**

两层防线：

1. 提示词层：告诉模型"修复建议里引用 URL 时，逐字照抄输入里的 url 字段"。
   注意用正面表述，别写"禁止/不要"这类否定式强约束——历史上有一次模型节点卡死就是它引起的。
2. 渲染层：⑧ 的 `_guard_urls()` 会把报告文本里与实测域名编辑距离 ≤ 2 的近似域名回正，
   并在运行数据里报告纠偏处数；无关域名（如 `example.com`）原样保留，不会误纠。

对应用例：`framework/platform/test_report_url_guard.py`（错域名回正、无关域名不误纠，两条都通过）。

## 九、⑤b 跑了但没贡献结果，怎么判读

⑤b 的运行状态是"成功"，不代表它交出了结果。看 ⑥ 的第二行诊断即可分辨：

| 诊断显示 | 含义 | 处理 |
| --- | --- | --- |
| 字符数=2，`[]` | 工具这轮没发现新问题 | 正常。要演示双线就得换个必然命中的检查 |
| 字符数很大，形状是"非 JSON" | ⑤b 输出的是自然语言段落 | ⑥ 会忽略它。提示词里要求"只输出 JSON 数组"，或用平台的结构化输出 |
| 字符数很大，形状是 JSON 数组 | 有结果，但可能已与被动线合并 | 看"两线交叉印证"条数，不要只看"工具线 N 条" |

来源构成现在分三档：被动检测线（⑤）、工具线（⑤b + MCP）、两线交叉印证，三者相加等于去重后的条数。
**"两线交叉印证"是演示里最有说服力的数字**——它同时证明了两件事：工具编排真的跑通了，
而且跨来源去重与关联是有效的（两条独立来源同时命中，误报概率显著下降）。

想让这个数字稳定出现，建议再挂一个 **Nuclei 漏洞扫描** MCP：在缺安全响应头的站点上它必然命中
`http-missing-security-headers` 模板，而被动线也会报同一组头缺失，两条线会合并成一条交叉印证的结论
（本地已用该场景验证：`tools=['headers-baseline','nuclei']`，置信度 0.80 → 0.95）。
**SQLmap 保持禁用**——主动注入与赛题"避免破坏性测试"的要求冲突。

挂上第二个 MCP 之后必须同步改的 5 处（白名单、提示词、超时、输出契约、⑥ 的引用），
以及可直接复制的双工具提示词：`framework/platform/tool_planner_prompt_dual.md`。

## 十、⑤c 规范化节点：给工具线加一段保险丝

实测到的典型现象：⑤b 运行成功，`tool_findings_payload` 有 463 个字符，内容却是
"非常好！现在我有了完整的证书信息。让我分析一下：……"——**自然语言，不是 JSON 数组**。

原因是 Agent 类节点的输出等于模型的最终回复，模型调完 MCP 后习惯写一段总结。⑥ 的容错规则会
忽略这种输出（设计如此，避免把散文当证据），结果就是"工具线跑了但没有结果"。

解决办法是加一个代码节点 ⑤c 做规范化，把接线改成 `④ → ⑤ → ⑤b → ⑤c → ⑥`：

| 节点 | 参数 | 引用 |
| --- | --- | --- |
| ⑤c | `tool_payload` | 5b_自规划_工具编排 → `result_key` |
| ⑤c | `scope_payload` | 3_代码_策略校验与上下文构建 → `result_key` |
| ⑥ | `tool_findings_payload` | **⑤c**（不再直接引用 ⑤b） |

⑤c 的代码：`framework/platform/tool_norm_code_node.py`，处理四类输出：

1. 上游直接给 JSON 数组 → 原样采用；
2. 上游给对象（`findings` / `results` / `items` / `data`）→ 取其中的数组；
3. 自然语言 + 内嵌 JSON（代码块或裸数组）→ 抠出"像风险清单"的那一段，优先取靠后的；
4. 纯自然语言、抠不出 JSON → 输出 `[]`，把原文摘要放进 `note`，**不猜、不编造**。

同时补齐缺字段：缺 `url` 用授权范围里的域名补、`severity` 缺省 medium、`tool` 缺省"自规划工具线"。

对应用例：`framework/platform/test_tool_norm_node.py`（四类输入全部通过，用例 1 用的就是你这次
⑤b 的原文）。

## 十一、⑦ 模型节点反复卡在"运行中"

⑦ 是全链路里唯一会被输入规模直接拖死的节点：它的输出长度 ≈ 风险条数 × 每条要写的字段。
工具线一挂上（Nuclei 那次），⑥ 交出来的条目变多、证据变长，模型写出合法 JSON 的难度上升；
超长或被截断后，平台的输出校验会反复重试，界面就一直是"运行中"。

三步处理，前两步不用改代码：

1. **⑦ 的异常配置**：失败后继续 + 自定义返回 `{"result_key": "[]"}`。
   ⑧ 有三级降级（上游 ⑦ → 自调模型 → 内置模板），⑦ 卡住不该拖死整条线。
2. **⑦ 的超时**：从默认值降到 300 秒，让它快速失败而不是无限转圈。
   若 ⑦ 配了 JSONPath / 结构化输出校验，把它放宽或改成可选——校验不通过就重试是空转的常见原因。
3. **加 ⑥b 裁剪节点**（根治）：`framework/platform/explain_prep_code_node.py`

| 节点 | 参数 | 引用 |
| --- | --- | --- |
| ⑥b | `findings_payload` | ⑥ 去重验证分级 → `result_key` |
| ⑦ | 输入（原引用 ⑥ 的那个） | **⑥b** → `result_key` |
| ⑧ | `explain_payload` | ⑦（不变） |
| ⑧ | `findings_payload` | ⑥（不变，报告渲染仍用完整数据） |

⑥b 做三件事：字段瘦身（去掉 `affected_urls` / `tools` / `source_lines` 等渲染字段）、
证据截断到 160 字、只送风险最高的 12 条（其余由 ⑧ 兜底补齐）。
本地实测 20 条 × 400 字证据的负载从约 40 000 字压到 5 000 字。

对应用例：`framework/platform/test_explain_prep_node.py`。

## 十二、⑤b 自己卡在"运行中"

⑤b 是整条链路上唯一执行"重活"的节点：Nuclei 是模板化扫描器，默认模板集有数千个模板，
叠加模型可能多轮调用工具，节点耗时从秒级跳到分钟级很正常。所以它显示"运行中"时，
先分清楚是**慢**还是**死**：

- 点"查看运行结果"看有没有中间的工具调用记录：有记录且在增加 → 慢，等；
- 超过节点超时（比如设了 900 秒）还不停 → 死，按下面的顺序收紧。

收紧顺序：

1. **超时降到 300 秒**。异常配置是"失败后继续"，最坏情况 5 分钟就退出，不会拖死主线。
2. **给提示词加调用预算**（已写进 `tool_planner_prompt_dual.md` 的【耗时与调用预算】）：
   工具调用最多 4 次、Nuclei 只跑 4 类配置与暴露模板且模板数 ≤ 20、单目标 ≤ 180 秒、目标数 ≤ 3。
   没有预算约束时，模型很容易"换个参数再扫一次"，看起来就是无限运行。
3. **分阶段回退定位**：先只挂 Nuclei 跑一次，再只挂 SSL 跑一次，确认慢在谁身上，然后再两个一起挂。
4. **演示保底**：⑤b 是增强线，主线 `④ → ⑤ → ⑥ → ⑦ → ⑧` 本身就能出完整报告。
   演示时先跑主线、展示报告，再单独展示工具编排与"两线交叉印证"，不要把它放在关键路径上。

### "运行中且完全没有输出"怎么判

Agent 类节点的运行结果只在结束时落盘，所以"运行中 + 结果面板空白"本身不能说明它死了。
要拿到确定性结论，只能靠超时：

1. 把 ⑤b 的节点超时改成 **120 秒**，再跑一次；
2. 2 分钟内返回（无论成功还是走了"失败后继续"的 `[]`）→ 说明只是慢，按实际耗时放宽到 300；
3. 超过 120 秒仍然显示运行中 → 不是"扫描慢"，而是卡在某个调用上。常见两种：
   - Nuclei 首次运行需要拉取模板（访问 GitHub），容器无外网或代理时就会一直等待；
   - MCP 调用报错后模型反复重试，形成隐形循环——提示词里的【耗时与调用预算】正是为此。

确认是后者时，两个选择：一是把 Nuclei 从 ⑤b 上摘掉，只保留轻量的 SSL TLS检测；
二是换一个更轻的第二工具（证书透明查询、子域名发现、HTTP参数发现），保持"两线"的演示结构，
但把单次耗时压到秒级。

## 十三、多挂 MCP 工具后的配置改动

提示词：`framework/platform/tool_planner_prompt_multi.md`（四个工具的边界逐条钉住，可直接复制）。

| 配置项 | 改成 | 原因 |
| --- | --- | --- |
| `TOOL_WHITELIST` | 列出全部已挂工具 | 白名单只有 SSL 检测时，模型即使看见其他工具也不会调用 |
| `MAX_QPS` | 3 | HTTP 参数发现会产生大量请求 |
| `BLOCKED_ACTIONS` | 追加 `端口扫描,OS探测,NSE脚本,目录爆破,参数爆破,fuzz,压测` | 与提示词的边界呼应 |
| 节点超时 | 300 | 四个工具的最坏耗时是它们之和，长超时等于放任它转圈 |
| ⑥ 的 `tool_findings_payload` | 引用 ⑤c | ⑤c 负责把散文/JSON 归一 |

工具取舍：

- **SSL TLS检测**：秒级只读，保留（已验证可用）。
- **子域名发现**：轻量，但产出的是"范围外资产线索"，必须只登记不探测。
  ⑤c 会把 `pending_assets` 透传到日志，报告里可以用来说明"发现范围外资产但未触碰"。
- **HTTP参数发现**：中等风险，用单 URL ≤ 50 次请求、5 QPS 限住。
- **Nmap网络扫描**：中高风险，唯一可能被判"超出网站巡检授权范围"的工具。
  授权书只写"网站安全检测"时建议直接摘掉——三个工具同样能演示"按目标选工具"。

## 十四、工具线结论定性的两条修正（实录）

线上出现过一条 `TLS 证书链验证失败`，被判成 `needs_review` + 置信度 0.35 +
证据写"复采未命中，疑似已修复或误报"。这是**误判**：证书链是协议层结论，
用一次 HTML 复采永远不可能命中，不能因此暗示"风险可能已经修好了"。修正两条：

1. **工具线结论不被 HTML 复采否定**。工具线命中、但复采的页面文本里找不到验证线索时，
   状态标 `unverified`、**置信度保持原值**，证据追加"工具线结论，HTML 复采无法验证
   （协议层问题不在页面文本里），需用同一工具复测后定性"。只有被动线的结论才允许
   判"复采未命中 → 疑似已修复"并降置信度。
2. **TLS 问题按子类分开**。证书链不完整、自签名、证书过期、弱协议、弱加密套件是五件
   不同的事，之前会被笼统归成同一条（`MISCONFIG.TLS_CONFIG`），等于把不同问题并掉。
   现在分别归一为 `SSL_TLS.CERT_CHAIN` / `SELF_SIGNED` / `CERT_EXPIRING` /
   `WEAK_PROTOCOL` / `WEAK_CIPHER`，判不出子类时才落到通用规则。

对应用例：`framework/platform/test_dedup_tool_line.py` 的用例 1~4。

## 十五、误报治理：六层处置

误报不是"算法不够聪明"，而是六种不同来源的问题，要分层处理。

| 误报来源 | 表现 | 处置层 |
| --- | --- | --- |
| 采集抖动（网络、WAF、缓存） | 这一秒有、复采就没了 | L2 复采确证 + 抖动重试 |
| 工具自身局限 | 如 sslscan 缺本地 CA，误报"证书链失败" | L3 来源分层（工具线不冒充确证） |
| 同一问题多来源重复报 | 被动线与工具线各报一次同名问题 | L1 去重合并 + 交叉印证 |
| 模型改写证据 | 域名抄错、证据被润色 | L5 渲染层纠偏 + 只让模型写影响与建议 |
| 有意配置 / 已知例外 | 自签名证书是有意为之、测试页含样例关键词 | L4 白名单抑制 |
| 规则过泛 | 同一响应头在多节点/CDN 上不一致 | L4 抑制 + L6 人工复核回写 |

已实现的部分：

- **L1 去重与交叉印证**：`_dedup_key`（类型 + 归一化规则 + 归一化位置）、
  `source_lines`（两线同时命中标 `both` 并提置信度）。
- **L2 复采确证**：`_confirm()`——第一次复采没命中会再采一次，命中即确证并注明"响应存在抖动"；
  两次都没命中才转 `needs_review` 并把置信度减半。只有疑似误报才多花一次请求。
- **L3 来源分层**：工具线结论不带可复采线索时标 `unverified` 且不抬置信度；
  协议层结论（证书链、端口、TLS 套件）不被 HTML 复采否定。
- **L4 白名单抑制**：⑥ 的新入参 `suppress_payload`（JSON），命中即标 `suppressed`，
  跳过复采、不计入风险统计，但保留在报告附录与审计记录里。
- **L5 报告透明化**：每条结论带状态与置信度，正文标注检测来源与是否交叉印证，
  运行数据里多一行"误报处置：复采未命中转待复核 X 条 · 白名单抑制 Y 条 · 工具线待工具复测 Z 条"。

抑制规则示例（传给 ⑥ 的 `suppress_payload`）：

```json
{
  "rules": [
    {"rule_id": "SSL_TLS.SELF_SIGNED", "url": "intranet.example.gov.cn",
     "reason": "内网系统使用自签名证书，属已知例外"},
    {"rule_id": "LEAK.KEYWORD", "title_contains": "内部资料",
     "reason": "该页面为联调环境，样例数据属已知例外"}
  ]
}
```

规则里写了哪几个字段就按哪几个字段做 AND 匹配，写空的字段不参与判断，
所以一条规则可以细到某个 URL、某个工具、某个严重度。

**待接的一层：L6 复核回写。** 平台没有变量赋值节点，所以闭环的做法是：
⑨ 复核节点收集人工判定 → 下一轮把结论作为 `suppress_payload` 传进 ⑥ →
同一问题不再进入正文，但仍在附录里可见。这样"告警 → 复核 → 复测不再告警"就是一条闭环。

对应用例：`framework/platform/test_false_positive_control.py`（抖动重试、抑制生效、
附录留痕三项，均通过）。

## 十六、报告下载怎么实现

原来 ⑧ 里那段导出代码有两个问题：`task_id` 根本没定义（就算平台支持文件桶也会抛异常），
而且没有兜底——所以"报告可下载"这条要求此前实际上是空的。现在改成**四种格式 + 三级落地**。

### 四种格式

| 格式 | 用途 | 说明 |
| --- | --- | --- |
| HTML | 交付与归档 | 自包含单文件（样式内联、无外部依赖），离线可打开，浏览器"打印 → 另存为 PDF"即得 PDF |
| CSV | Excel 分析 | 带 UTF-8 BOM + CRLF，Excel 双击不乱码；含"是否抑制"列 |
| Markdown | 归档 / 进 Git | 纯文本，便于评审检索与版本对比 |
| JSON | 二次加工 | 结构化全量数据，可直接接 CMAP/看板；**完全来自结构化字段，不含模型改写，最可信** |

### 三级落地（按平台能力自动退化）

1. **平台文件桶**：代码节点里能用 `FileBucket()` 时，四种格式落盘并在交付区标注路径，
   用户在运行结果面板的文件页签下载；
2. **data URI 链接**：把报告内容 base64 内嵌成可点击链接，对话里直接点开下载
   （受客户端策略限制，HTML 超过 90 KB 时不内嵌，只保留 CSV 链接）；
3. **文本内交付**：前两条都不通时，正文里就是完整报告，复制另存为 `.md` 即可；
   HTML 依然可用浏览器打开打印成 PDF。

### PDF 怎么做

不在代码节点里生成 PDF——平台没有 PDF 依赖库，硬凑容易翻车。可行路径是
**自包含 HTML → 浏览器打印 → 另存为 PDF**，交付区里写了操作步骤；
如果平台后续提供文档类工具节点或 MCP，再接一招"HTML 转 PDF"即可。

### 平台侧要确认的三件事

1. 代码节点里 `FileBucket` 是否可用：跑一轮看日志，会出现
   `平台未提供文件桶，改用文本内交付` 或具体落盘路径；
2. 节点库 / MCP 列表里有没有文件、文档类工具——有的话用工具节点承接上传，链接更稳；
3. 对话客户端是否允许点击 `data:` 链接——跑完点一次就知道。

对应用例：`framework/platform/test_report_export.py`（无文件桶、注入文件桶、
CSV Excel 兼容、HTML 自包含四项，均通过）。

配套的提示词补丁写在 `framework/platform/tool_planner_prompt_single.md` 的"输出契约"一节：
告诉模型"你的最终回复就是接口返回值"，并明确空结果就直接回 `[]`。提示词 + ⑤c 两层，链路就不再
依赖模型是否守约。
